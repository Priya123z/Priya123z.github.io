How I structure automation

Every framework I have built has ended up in roughly this shape, because it is the shape that answers one question fastest: something went red at 3am, where do I look? Four layers, each allowed to call only the one below it, so the answer falls out of the stack trace instead of out of an hour of reading.

A layer may call downwards. It may never call upwards or sideways.

That is the whole rule, and it is worth being pedantic about, because the value only arrives when there are no exceptions. One test that reaches past its flow and grabs a selector directly is not a small shortcut. It is the thing that turns "the checkout page changed" from a one-file edit into a search across the suite.

One test, all the way down

This is a real test from the framework, and every line below it is the code it actually reaches. Read it downwards: each box only knows about the one under it.

  1. 1
    The test tests/UI/test_login.py
    def test_login_user(page, registered_user):
    home = HomePage(page)
    signup_login = home.navbar.open_signup_login()
    signup_login.login(registered_user.email, registered_user.password)

    assert home.user_logged_in()

    Six lines, and every one of them is a sentence about the product. No URL, no selector, no wait, no browser. The only assertion in the whole trace is the last line, and that is on purpose: if this file goes red, the expectation was wrong or the product was.

  2. 2
    The fixtures it asked for conftest.py
    page               # a browser, already launched and configured
registered_user    # a real account, already created through the API

    The test names two things it needs and gets them. It does not know that page came from a factory that read an env file to decide on Chromium and headless, or that registered_user was created over HTTP because doing it through the UI would cost fifteen seconds a test. Setup that fails is a fixture error, not a test failure, and the report says so.

  3. 3
    The page object pages/signup_login_page/signup_login_page.py
    self._login_email    = page.locator("[data-qa='login-email']")
self._login_password = page.locator("[data-qa='login-password']")
self._login_button   = page.locator("[data-qa='login-button']")

def login(self, email, password) -> HomePage:
    self.fill(self._login_email, email, "Login Email")
    self.fill(self._login_password, password, "Login Password")
    self.click(self._login_button, "Click on Login Button")
    home = HomePage(self.page)
    home.is_loaded()
    return home

    The only file in the trace that knows what the page looks like. Two things worth pointing at: the selectors are attributes set once in the constructor rather than strings scattered through methods, and login() returns the page you end up on. That return is what lets the test read as a journey without the test ever naming a navigation.

  4. 4
    The base page pages/base_page.py
    def click(self, locator, description):
    self.wait_for_visibility(locator, description)
    return self._execute_action(
        action=lambda: locator.click(),
        operation="Click",
        locator=locator,
        description=description,
    )

    Nobody calls Playwright directly. Every interaction goes through here, which is why waiting, logging and the screenshot-on-failure are consistent across a hundred call sites instead of being remembered ninety-four times. description is not decoration: it is what turns a failure into "Failed Click: Login Button" rather than a locator string nobody can read at a glance.

The four layers

Same idea stated as rules rather than as a walkthrough. The column that does the real work is the last one, because a layer is defined by what it is not allowed to contain.

Tests may call flows
tests/UI/tests/api/

Reads like the requirement, and holds the assertions. Never holds a selector, a URL, a wait, or a piece of setup.

Flows may call pages and clients
flows/UI_Flow/flows/API_Flow/

Journeys that more than one test needs: register, log in, add to cart, check out. Never holds an assertion. A flow that asserts is a test pretending to be a helper, and the failure surfaces in the wrong place.

Pages and API clients may call services
pages/api/api_client.pymodels/

The only place that knows what the app looks like: every selector, every endpoint, every response model. Never holds test data or a decision about what should happen, so a redesign is one file per screen.

Shared services calls nothing above
config_managerbrowser_factoryauthentication_managerartifact_manager

Config, browsers, auth state, readers and writers, artifacts, reached through fixtures. Never holds anything about this particular product, which is the test that decides whether something belongs here at all.

Evidence written by every layer
alluretracesscreenshotslogs

Everything lands in one run folder keyed on a single execution id shared by every worker. A failure arrives as a trace you can replay in the Playwright inspector, not as a stack line and a guess.

What this buys, concretely

The layering is not tidiness. It is a lookup table from what you saw to where you go, and it only works if the rule was kept everywhere.

What went redWhere it isBecause
An assertion failed tests/ Assertions live nowhere else, so either the expectation is stale or the product is genuinely broken. Nothing else can produce this.
Timed out waiting for an element pages/ Selectors live in exactly one layer. The screenshot is already attached and the log line already names the element in English.
Half the suite failed at the same step flows/ A shared journey broke. One fix, not fifteen, and the count of failures is what tells you which layer to open.
A response no longer matches its schema schemas/ Validation runs on every API response, so a renamed field fails loudly here instead of passing quietly on a 200 and breaking a UI test tomorrow.
Everything failed before the first test conftest.py Setup, not product. Pytest reports a fixture error separately from a test failure, which is the difference between "the environment is wrong" and "the code is wrong".

The shared execution id in the evidence layer was a real bug, not a design flourish. Each xdist worker is its own process, each one stamped its own timestamp, and a run split itself across two folders. CI then published whichever one it found first, which was sometimes the one with almost nothing in it. A green report over a half-empty folder is worse than a red one, because nobody goes looking. The id is now generated once by the controller and passed down through an environment variable, and every worker writes into the same place.
